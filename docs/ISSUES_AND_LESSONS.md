# 工程错误复盘、根因分析与防复发措施

**范围**：从早期工程组织经验到 2026-11-21 代码/网页/协议联调故障。按 `现象→根因→处理→回归→残留风险` 描述。具有 Git SHA 的故障以仓库历史为据；“历史团队经验”来自 [原始错误笔记](../item/docs/error.md)，不能伪造具体日期或硬件测试视频。

## 1. 总体结论

这个项目反复出现的不是某一个单独算法错误，而是五类边界被混淆：
1. 竞赛任务规则与硬件选型的先后顺序；
2. V4/V5/ULog43/CAR-LINK 之间的协议与版本；
3. PC 软件回环、TEST 假 MCU 和 REAL 真正实测；
4. 浏览器图形流畅度与控制消息真正可用性；
5. 机械 CAD 的层级与第五轴到底带动哪些部件。

解决它们需要**接口合同、来源标记、明确控制权、可重复回归、实机验证记录**，而不只是增加更多页面和功能。

## 2. 早期项目管理与硬件教训（来自 `item/docs/error.md`）

| 记录的错误/教训 | 造成的风险 | 落地规则 |

## 3. Git rebase/合并冲突导致代码误删除风险

**现象**：早期本地 `git pull --rebase --autostash` 依次冲突于 `sim2real/web_mode_gateway.py` 与 `sim2real/web/mode_router.js`。一次冲突处理后 Git 输出 `rewrite sim2real/web_mode_gateway.py (100%)`、`2 files changed, 2 insertions(+), 321 deletions(-)`，随后仍有未解决冲突。直接 `car` 运行含 `<<<<<<<` 的 Python 文件会失败。

**根因**：把 `git show :2:path` 当作在所有 rebase 步骤中都可读取；实际当次冲突在 `mode_router.js`，`web_mode_gateway.py` 已是暂存态 `:0:`，没有 `:2:`，重定向先把工作区文件截断，再因插入锚点失效导致还原不完整。另一个风险是多个本地与远程功能同时改同一网关路由位置。

**处理**：停止继续叠加冲突，创建备份分支并 `git rebase --abort`，保存 autostash 后核查 `git status`；后续将功能通过隔离工作树、合并提交和专门测试逐步整合，避免在冲突文件中直接执行损坏服务。

**防复发**：
- 先执行 `git status`、`git ls-files -u`、`git show REBASE_HEAD`，只有**当前冲突文件存在 stage 2/3** 时才读取它们。
- 永不直接用不确定成功的 `git show :2:file > file` 覆盖唯一工作文件；先写 `/tmp/file.stage2` 并检查非零大小/状态。
- 冲突后做 `git diff --check`、`python3 -m py_compile`、针对路由的回归测试，再 `git add`/`git rebase --continue`。
- 不以 `git rebase --skip`、`reset --hard` 或清理工作树作为默认“修复”方法；先备份用户修改。
- 保留功能状态不等于保留全部历史；合并前检查 `merge-base` 与文件 diff，合并后核对输出树。

## 4. OpenMV V4 与旧 V5 口径不一致

**现象**：早期视觉四文件版采用 `#SEQ/#SLOT/#ARM/#OBJ/#TAKE`，而 STM32 正式 UART3 接收层使用 `@SEQ,LEN,BODY*XX<LF>` 的 V4 校验帧。仅把串口号写成一致，双方仍不理解彼此任务/状态。

**根因**：协议名相近但格式、任务生命周期、参数数量和完成定义不同；主控可能允许发送任意 `JOB` 编号，但相机对应 V4 分支只实现其中一部分。

**修复**：`algorithm/openmv/openmv_all/config.py` 现默认 `UART_PROTOCOL='V4'`；`serial.py` 同时保留可选 V5；通过协议对齐文档和 OpenMV 主机测试明确当前 V4 消息。历史 V5 算法和 25 步任务模型仍保留，不默认为实车完整闭环。

**未解问题**：`JOB,40` 初次锁盘仍依赖三异色布局；希望“看到两件即可确认”需要新的几何/历史定位策略和误检率验证。`JOB,41` 夹爪像素与相机安装仍要标定；`JOB,42`、机械真实成功/失败回执的双端闭环不能靠文件存在证明。

## 5. V4 的 `AREA_OK` / `IDLE` 分帧竞态

**现象**：OpenMV 完成 `JOB,40` 可能连续发送 `AREA_OK,...` 和 `IDLE`，但 STM32 主循环先收到第一帧就试图发 `JOB,41`；此时相机仍 busy，启动被拒绝。

**根因**：协议上“区域已确认”和“视觉任务已释放”是两个事件，UART 中断或 DMA 分段到达不能保证应用层同一轮看到二者。

**解决**：主控必须同时依据已确认区域与 `VISION_IDLE` 状态发起下一任务，不依靠定长 `sleep` 猜时间。已有独立主机契约测试复现此差异；**真实串口抖动场景仍需验收**。

## 6. 键盘控制：能看到网页但小车不动

**现象**：用户在 `/keyboard` 看到紫色 MOCK 车却按键不动，或显示 `NO_KEYS_OR_TIMEOUT`。一些版本里按住键会停、鼠标长按 300ms 后中止、重置场景后恢复旧位置。

**根因可分层**：
1. 浏览器焦点在 slider/text、键盘事件未被捕获；
2. HTTP intent 没到或超过 300ms TTL；
3. PC ROS2 发布/独立订阅回环未启动或域 ID 不一致；
4. `/api/keyboard/dryrun` 被关闭、超时或未拿到合格订阅来源；
5. 旧的 HTTP 回复晚到覆盖更新后的 MOCK 位姿；
6. 把正常松键 `NO_KEYS_OR_TIMEOUT` 误当系统故障。

**修复历程**：`3b51f29e` 处理按住鼠标续期；`f0857765`/`03dc2940` 处理场景重置的序号/旧回包；`a8f7de06` 采用不需要 Shift 的直通本机 ROS2 演示；`e77c425b` 让“浏览器收到 W”和“服务器有有效速度”分开显示，并允许机构滑块获得焦点后用快捷键。

**排查原则**：
~~~text
浏览器是否显示捕获 W？
  ├─ 否：焦点、浏览器快捷键、物理键盘
  └─ 是：/api/keyboard/intent 是否有有效键与新时间？
          ├─ 否：HTTP/超时/本地安全门
          └─ 是：ROS2 pub 是否在线？订阅 echo 是否新鲜？
                  ├─ 否：ROS_DOMAIN_ID/节点/QoS/自动启动
                  └─ 是：/api/keyboard/dryrun 是否更新？
                          ├─ 否：订阅来源、轮询和模拟模型
                          └─ 是：检查 SVG 变换/浏览器缓存
~~~
`NO_KEYS_OR_TIMEOUT` 在松键时是正常停止；不能无条件判为 bug。`/keyboard` 默认是不考虑真实物理障碍的直接积分模式，不等于真实赛道可任意穿行。

## 7. 网页流畅度优化反而让小车“直接动不了了”

**时间线**：
- `ff8922b6`：为解决约 75ms 的新 ROS2/HTTP 位姿快照直接覆盖 SVG、产生“回弹”的问题，引入一个持久显示追踪器；
- 用户在 Ubuntu 报告“现在直接动不了了”；
- `07ffb4e8`：撤回有问题的追踪实现，恢复已知可动的数据/按键链；
- `9c1c35de`：只在 `renderMockPose` 的最终 SVG 展示中平滑坐标，保留原始 `motionSnapshot`、`renderMockPose(data)` 回退路径和原有 WASDQE/STOP 发送逻辑。

**根因归纳**：对“渲染层抖动”动用了控制采样和 STOP 状态机的重构，离线数值测试未完全覆盖真实浏览器异步输入和 ROS2 启动路径；表现为视觉功能改变破坏了可用性。

**预防**：控制/网络/网页展示分层；任何轨迹平滑不得虚构真实位置、提前发指令、撤销 deadman（松键即停）的停止约束；新增至少包含 **按键→发布→订阅→MOCK→绘制**、松键、断网、窗口失焦、缓存更新的回归。关键安全问题采用“先恢复可用基线，再小范围修正”的策略。

## 8. 机械自由度理解错误与 CAD 父子层级错误

**现象**：用户指出“这块还能转”，最初被误解为 PC7 三工位转盘；之后误实现为“车尾平台绕竖直轴旋转”。截图和继续沟通确认真正要转的是**升降立柱总成**，前端导轨、滑台、腕部与夹爪一起绕竖直轴转动。

**根因**：只有侧视图局部裁切，未先定义机械旋转轴/枢轴/子部件清单。为了快速出视觉效果，把 SVG 的旋转组错误挂在车尾托盘树上。

**修复**：
- `ab724fbe` 首先让 PC7 三工位在侧视图跟随正确角度；
- `ac736057` 的“平台旋转”被认定为错误概念；
- `d16841ed` 更名成 `column_yaw_deg`，在立柱下建立独立的 `columnTurn` 节点，导轨和夹爪作为子节点，PC7 托盘仍挂在底盘；
- `8da64acd` 扩展 ±180° MOCK，并修正侧视夹爪用带符号 cos 投影：从“朝前→侧面→朝后”，不是立柱倒下。

**仍需确认**：第五轴的真实驱动 GPIO/舵机/步进、减速比、零位、限位、线束允许旋转半径、避碰包络。网页模拟支持 180° **不等于真实硬件允许 180°**。

**预防**：每次新增机械轴前填表“转轴方向、旋转中心、运动主体、子部件、单位、范围、硬件通道、限位、归零、动作回执”；缺项则只能加入 MOCK 演示，不允许连接 STM32。

## 9. 测试工具自身错误造成的 CI 假阴性

**现象**：新增第五轴后完整 GitHub CI 的 OpenMV 用例出现 `Start directory is not importable`；另一次测试把“超范围角度应抛异常”作为断言，但模型设计实际采用 `clamp`，导致非产品故障的失败。

**根因**：
- Python 3.10 `unittest discover` 对 `-s/-t` 路径、测试目录作为包的条件严格；脚本仅靠相对目录或只改 `-s` 不够；
- 测试期望与接口合同不一致，把数值限幅误判为输入错误。

**修复**：
- `cfda1d44`：按既定 API 语义修正角度测试：范围外有限数 clamp，NaN/Inf 拒绝；
- `580409fb` / `f678e783`：逐步修正 unittest 发现时目录定位；
- `cb26b28a`：为 OpenMV 测试目录补 `__init__.py`，不跳过测试；
- 之后包含 OpenMV/STM32/JS 的全套软件 CI 在 [#44878008112](https://github.com/David-tiao/car/actions/runs/44878008112) 完成成功。

**预防**：测试失败先看完整 stderr/traceback，区分“实现错误、环境/路径错误、错误断言”；坚决不通过跳过测试、写死 PASS 或造硬件结果来让 CI 变绿。

## 10. 地图 V5/V6 边界与来源误用

**现象**：原料转盘在场地上边界附近，V5 图像生成时把外侧部分标成 occupied，V6 核对版说明与原版有 358 个栅格差异。

**根因**：圆盘占据判定没先排除场地外区域；坐标系原点、栅格范围、物理障碍和规则禁行被混画。

**修复/边界**：V6 核对版将场外保持 unknown，把 keepout 与物理图分开；不自动替换正在使用的正式地图，未做现场 TF、Nav2 keepout、膨胀半径或激光雷达复核。真实运行必须先核对配置读取的是哪个地图，不要因为文件名叫 V6 就认定部署了。

## 12. 团队协作防回归清单

每次改动至少回答：

1. **哪个模块拥有这项状态和控制权？**（OpenMV / STM32 / Pi ROS2 / TEST / 浏览器）
2. **消息的来源、单位、frame_id、时效、回执语义是否写全？**
3. **原有可工作路径是否还在？**（WASDQE、STOP、REAL odom、PC7、UART）
4. **测试是否覆盖错误、过期、重放、断线、互斥、边界和未标定？**
5. **有没有现场硬件证据？**没有时只能写“代码/模拟通过”。
6. **是否更新文档/变更历史？**纠正的错误必须指明旧方案已被废弃。
7. **是否能回滚而不丢工作？**先保留未提交改动和唯一分支，再做合并和清理。
