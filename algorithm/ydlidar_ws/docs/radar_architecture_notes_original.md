# ROS 2 雷达移动机器人系统开发笔记

## 1. 项目概述

### 1.1 项目目标

本项目基于 ROS 2 系统搭建移动机器人雷达感知与运动框架，实现雷达数据采集、下位机通信、机器人运动状态发布、SLAM 建图以及 RViz2 可视化等功能。

项目的核心任务包括：

1. **雷达驱动与数据采集**：启动雷达驱动节点，获取雷达扫描数据。
2. **上下位机通信**：建立 ROS 2 上位机与 STM32 下位机之间的通信，实现运动指令和状态数据的传输。
3. **机器人坐标系与 TF 变换**：建立机器人本体、雷达及里程计之间的坐标关系。
4. **里程计与运动状态发布**：根据编码器或其他运动传感器的数据，计算机器人运动状态，并发布里程计信息及 TF 变换。
5. **SLAM 建图**：融合雷达扫描数据和必要的运动信息，完成机器人周围环境的地图构建。
6. **RViz2 可视化**：显示雷达扫描数据、机器人坐标系、TF 变换和 SLAM 地图。

### 1.2 ROS 2 的基本通信机制

在 ROS 2 中，节点（Node）通过话题（Topic）、服务（Service）和动作（Action）等机制进行通信。

雷达本身并不是一个话题，而是由雷达硬件、驱动程序和驱动节点共同完成数据采集。雷达驱动节点通常通过话题发布扫描数据，其他节点订阅这些数据并进行处理。

例如：

- 雷达驱动节点发布 `/scan` 话题。
- SLAM 节点订阅 `/scan`，利用雷达数据进行定位与建图。
- STM32 通信节点负责传输下位机的运动指令和反馈数据。
- 里程计节点发布 `/odom` 话题，并根据系统设计发布相应的 TF 变换。
- RViz2 订阅地图和传感器数据，并结合 TF 关系进行可视化。

需要注意，**定位并不只是简单的发布者或订阅者关系，而是由算法节点订阅传感器数据、计算机器人位姿，并发布定位结果或坐标变换。**

### 1.3 系统总体数据流

```text
                   ROS 2 移动机器人系统

       ┌────────────────────────────┐
       │         雷达硬件            │
       └─────────────┬──────────────┘
                     │
                     ▼
       ┌────────────────────────────┐
       │       雷达驱动节点          │
       │      发布 /scan             │
       └─────────────┬──────────────┘
                     │
                     ▼
       ┌────────────────────────────┐
       │         SLAM 节点           │
       │   订阅 /scan 和 TF          │
       │   构建地图并估计位姿        │
       └─────────────┬──────────────┘
                     │
            ┌────────┴────────┐
            ▼                 ▼
       地图数据 /map      TF：map → odom
            │                 │
            └────────┬────────┘
                     │
                     ▼
       ┌────────────────────────────┐
       │          RViz2              │
       │   显示地图、雷达和机器人     │
       └────────────────────────────┘


       ┌────────────────────────────┐
       │       STM32 下位机          │
       │   电机控制、编码器反馈等     │
       └─────────────┬──────────────┘
                     │
              串口 / USB 等
                     │
                     ▼
       ┌────────────────────────────┐
       │     ROS 2 通信与里程计节点   │
       │  发送控制指令、接收反馈数据  │
       │  发布 /odom 和 odom → base_link
       └────────────────────────────┘
```

说明：

- 雷达驱动负责提供环境感知数据。
- STM32 负责底层电机控制及相关传感器数据采集。
- ROS 2 通信节点负责上下位机之间的数据转换和传输。
- 里程计模块根据编码器等数据估计机器人运动状态。
- SLAM 通常根据雷达数据、TF 和可用的里程计信息进行建图。
- RViz2 根据地图、传感器消息和 TF 树显示整个系统的运行状态。

实际的数据话题名称、节点职责和通信接口，应以使用的雷达驱动、STM32 固件及 ROS 2 软件包为准。

## 2. 雷达系统启动与准备

### 2.1 软件准备

雷达启动前，需要准备以下软件：

- ROS 2 运行环境。
- 对应型号的雷达驱动程序。
- 雷达驱动的配置文件。
- 雷达驱动依赖的 ROS 2 软件包及相关库。
- RViz2 可视化工具。
- 后续建图所需的 SLAM 软件包，例如 `slam_toolbox`。

雷达驱动配置文件中需要重点检查的参数包括：

- 雷达设备连接端口。
- 串口波特率（如果使用串口通信）。
- 雷达工作模式。
- 雷达数据发布的话题名称。
- 雷达坐标系名称，例如 `laser_frame`。

具体参数以雷达厂商提供的驱动文档为准。

### 2.2 固件准备

目前，雷达固件启动及相关配置尚未完成，需要进一步确认雷达模组的工作方式。

后续需要完成的工作包括：

1. 确认雷达型号及对应的固件版本。
2. 获取厂商提供的固件文件和烧录工具。
3. 确认雷达使用的烧录接口及硬件连接方式。
4. 根据厂商要求完成固件烧录或固件升级。
5. 确认雷达能够正常启动，并通过驱动程序输出数据。

**注意：固件烧录与无线连接并不是同一件事。** 如果雷达需要通过无线方式通信，还需要确认模组是否具备无线通信硬件，以及是否需要额外配置无线网络、通信协议或相关固件功能。

### 2.3 硬件准备

| 硬件 | 主要用途 |
|---|---|
| 雷达模组 | 获取环境扫描数据 |
| STM32 开发板或下位机 | 电机控制、编码器采集及底层运动控制 |
| 雷达转接板 | 根据雷达接口要求连接电源、通信线路或调试接口 |
| 上下位机通信线 | 建立 ROS 2 主机与 STM32 之间的通信 |
| 电机及驱动器 | 执行机器人运动指令 |
| 编码器或其他运动传感器 | 为里程计提供数据 |
| 稳定电源 | 为各模块提供符合规格要求的供电 |

实际需要的硬件取决于雷达接口、STM32 型号和底盘设计。

### 2.4 上下位机通信

ROS 2 通常运行在 Linux 主机上，而 STM32 负责底层实时控制。两者之间可以使用 UART、USB 转串口或其他适用的通信接口。

典型通信流程如下：

```text
ROS 2 上位机
    │
    │ 发送速度指令或其他控制指令
    ▼
STM32 下位机
    │
    ├── 控制电机
    ├── 采集编码器数据
    └── 返回运动状态
    │
    ▼
ROS 2 上位机
    │
    ├── 解析下位机反馈
    ├── 计算或更新里程计
    └── 发布 /odom 和 TF
```

需要明确上下位机通信协议，包括数据帧格式、数据长度、校验方式、发送频率、异常处理和通信超时策略。

如果 STM32 返回的是编码器计数值，通常还需要根据编码器分辨率、轮径、轮距和采样时间计算机器人的线速度、角速度及位姿变化。

## 3. 移动机器人的坐标系框架

### 3.1 REP-105 概述

REP-105 的英文名称为 *Coordinate Frames for Mobile Platforms*，即移动平台的坐标系框架。

该提案规定了 ROS 中移动机器人常用坐标系的命名、语义和层级关系，旨在提高机器人驱动、定位、导航和感知等软件组件之间的兼容性。

在本项目中，需要重点理解以下坐标系：

- `base_link`
- `odom`
- `map`
- `laser_frame`

在需要全局地理参考或多地图协同的系统中，还可能使用 `earth` 坐标系。

### 3.2 核心坐标系的含义

| 坐标系 | 含义 | 主要用途 |
|---|---|---|
| `base_link` | 固定在机器人本体上的参考坐标系 | 表示机器人本体及传感器相对位置 |
| `odom` | 连续的局部世界坐标系，可能随时间产生累计漂移 | 短期运动估计、局部控制和感知 |
| `map` | 长期相对稳定的世界坐标系，但定位更新可能造成离散跳变 | 地图构建、全局定位和导航 |
| `earth` | 地球地心地固坐标系（ECEF）的参考原点 | 可选的全局地理参考 |
| `laser_frame` | 雷达自身的传感器坐标系 | 表示雷达扫描数据所在的参考坐标系 |

其中，`laser_frame` 不是 REP-105 强制规定的固定名称，而是项目中常见的一种雷达坐标系命名方式。实际名称必须与驱动配置和消息中的 `frame_id` 保持一致。

### 3.3 `map` 与 `odom` 的区别

`odom` 和 `map` 都可以作为机器人位置的参考，但它们的作用不同。

**`odom`：连续但可能漂移**

- 通常由轮式里程计、视觉里程计或其他运动估计模块提供。
- 机器人在该坐标系中的位姿应连续变化。
- 随着运动时间和距离增加，误差可能逐渐累积。
- 适合局部运动估计和需要平滑运动的任务。

**`map`：长期相对稳定，但可能跳变**

- 通常由 SLAM 或定位系统维护。
- 通过环境观测修正累计误差。
- 当定位结果更新时，机器人在 `map` 中的位置可能出现离散变化。
- 适合地图构建、全局定位和导航。

因此，不能简单地将 `map` 和 `odom` 合并为同一个坐标系。

### 3.4 TF 树的层级关系

REP-105 推荐的核心坐标系关系如下：

```text
earth
  └── map
       └── odom
            └── base_link
                 └── laser_frame
```

这里的 `earth` 是可选的。如果项目不需要地理参考，可以从 `map` 开始：

```text
map
 └── odom
      └── base_link
           └── laser_frame
```

各坐标系之间的关系如下：

- `map → odom`：由 SLAM 或定位组件发布。
- `odom → base_link`：由里程计或运动估计组件发布。
- `base_link → laser_frame`：由机器人模型或静态 TF 发布器描述。
- `earth → map`：仅在需要全局地理参考时使用。

TF 使用树形结构组织坐标系。每个坐标系只能有一个父坐标系，但可以有多个子坐标系。

### 3.5 雷达坐标系的建立

雷达通常安装在机器人底盘上，因此需要描述雷达相对于机器人本体的位置和朝向。

例如：

```text
base_link
   └── laser_frame
```

这表示雷达坐标系固定连接在机器人本体坐标系上。

如果雷达安装在底盘前方、上方或具有一定倾斜角度，需要根据实际安装位置和姿态配置相应的平移与旋转参数。

雷达与机器人本体之间的变换通常可以通过以下方式发布：

1. 在 URDF 中描述雷达安装位置，并通过 `robot_state_publisher` 发布。
2. 使用 `static_transform_publisher` 发布静态 TF 变换。

如果雷达驱动本身已经发布相关 TF，需要检查是否与其他节点重复发布同一条变换。

## 4. 各坐标变换的发布职责

### 4.1 `odom → base_link`

该变换描述机器人本体相对于局部里程计坐标系的位置和姿态。

通常由里程计或运动估计组件发布，例如：

- 根据轮式编码器计算的差速底盘里程计。
- 视觉里程计。
- 融合 IMU 和编码器数据的状态估计模块。

在本项目中，如果 STM32 负责采集编码器数据，那么 ROS 2 上位机可以接收这些数据，计算机器人运动状态，再发布里程计话题和对应的 TF。

### 4.2 `map → odom`

该变换通常由 SLAM 或定位组件发布。

SLAM 根据雷达扫描数据和其他可用信息估计机器人在地图中的位姿，再结合里程计结果，计算地图坐标系与里程计坐标系之间的关系。

例如，使用 `slam_toolbox` 建图时，SLAM 节点通常负责发布 `map → odom`。

### 4.3 `base_link → laser_frame`

该变换描述雷达相对于机器人本体的固定安装关系。

由于雷达与底盘之间的相对位置通常不会改变，因此一般使用静态 TF 或 URDF 描述。

### 4.4 坐标变换汇总

| TF 变换 | 典型发布者 | 是否通常为静态 |
|---|---|---|
| `map → odom` | SLAM 或定位节点 | 否 |
| `odom → base_link` | 里程计或运动估计节点 | 否 |
| `base_link → laser_frame` | `robot_state_publisher` 或静态 TF 发布器 | 是 |
| `earth → map` | 全局定位组件或静态 TF 发布器 | 视具体配置而定 |

**注意：每一条 TF 变换都应有明确的发布者，避免多个节点同时发布同一条变换。**
