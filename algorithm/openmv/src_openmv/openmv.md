# 工创小车视觉方案需求说明

> **项目名称：** 工创小车视觉识别系统  
> **上位机硬件：** OpenMV H7 Plus  
> **算法类型：** 传统机器视觉算法  
> **原始代码参考：** src_openmv  
> **当前开发阶段：** 五个独立视觉测试单元的开发与验证

---

# 一、项目概述

## 1.1 项目定位

本项目为工创小车的视觉识别方案，由 OpenMV H7 Plus 作为视觉上位机，负责识别二维码、物料、色环、黑色边线及蓝色矩形框。

视觉系统需要为后续小车底盘运动、物料搬运及机械机构动作提供准确的视觉信息。

## 1.2 上位机硬件与算法

| 项目 | 说明 |
|---|---|
| 上位机硬件 | OpenMV H7 Plus |
| 视觉算法 | 传统机器视觉算法 |
| 原始代码参考 | src_openmv |
| 开发环境 | OpenMV MicroPython |

## 1.3 原始代码参考要求

在编写或修改代码之前，必须完整参考现有的 `src_openmv` 项目。

参考范围包括：

- 文件组织方式、代码格式及命名规范；
- OpenMV 摄像头初始化及图像采集方式；
- 现有视觉算法、识别条件、阈值及参数；
- 函数调用方式、语法习惯及运行环境要求；
- 已有的串口配置、数据输出方式及辅助逻辑。

**核心原则：**

以现有 `src_openmv` 项目已经确定的识别规则和算法为依据，不得擅自改变物料、色环等目标的判定标准。

如确实需要调整算法或参数，应先说明调整原因，再进行实测验证。

# 二、第一阶段：五个独立视觉测试单元

## 2.1 总体要求

第一阶段需要提供以下五个独立测试单元：

1. `demo_scan.py`
2. `demo_material.py`
3. `demo_circle.py`
4. `demo_edge.py`
5. `demo_edge_blue.py`

所有测试单元必须遵守以下要求：

- 一个测试单元对应一个独立文件。
- 文件名称必须与上述名称一致。
- 每个文件只负责验证对应的一项视觉功能。
- 测试阶段不拆分为 `config.py`、`utils.py` 等多个文件。
- 每个测试文件应能够独立运行。
- 可以在单个文件内部定义必要的小函数或类，但不得增加不必要的外部依赖文件。
- 算法、识别条件和参数必须遵循 `src_openmv` 中已有的项目规则。

## 2.2 demo_scan.py：二维码扫描测试

### 测试目标

单独验证 OpenMV H7 Plus 的二维码扫描与解码功能。

### 功能要求

1. 初始化摄像头并持续采集图像。
2. 检测画面中的二维码。
3. 完成二维码定位与内容解码。
4. 将识别结果以便于观察的方式显示或输出。
5. 二维码要一直框住

### 本测试单元的范围

只验证二维码扫描和解码功能。

不负责根据二维码内容规划底盘路线，也不负责执行后续物料搬运动作。

### 验收重点

- 能否稳定检测到画面中的二维码。
- 能否正确解码二维码内容。
- 二维码位置或内容发生变化时，识别结果是否能够正确更新。

## 2.4 demo_circle.py：色环识别测试

### 测试目标

单独验证 OpenMV 对色环及其对应数字的识别能力。

### 功能要求

1. 按照 `src_openmv` 中已经确定的色环识别算法和规则进行识别。
2. 识别色环目标，并尽可能正确读取色环上的数字。
3. 将识别到的数字及必要的识别状态输出或显示，便于测试和核对。

相关映射规则以项目已有说明文件为准。

### 本测试单元的范围

不执行夹取、放置或机械机构运动。

物料与色环之间的对应关系将在后续系统整合阶段使用。

- 能否读取色环上的数字。

## 2.5 demo_edge.py：黑色边线识别与停车信号测试

### 测试目标

单独验证 OpenMV 对黑色边线的识别能力，并测试近距离停车信号的输出。

### 功能要求

1. 检测图像中的黑色边线。
2. 判断黑色边线与 OpenMV 之间是否达到设定的近距离条件。
3. 当检测到黑色边线距离过近时，向下位机发送停车信号。
4. 在测试过程中输出必要的检测状态，便于观察边线位置和停车触发时机。
5. 屏幕实时显示距离与标定黑线的位置

### 关键要求

停车信号必须由黑色边线的近距离检测条件触发。

不能仅仅因为画面中出现黑色区域就直接触发停车。

### 本测试单元的范围

只验证：

- 黑色边线检测；
- 距离或接近程度判断；
- 停车信号触发逻辑。

具体通信数据格式应与后续统一通信协议保持一致。

在协议尚未确定前，不得自行将临时测试格式当作最终通信协议。

### 验收重点

- 能否稳定识别目标黑色边线。
- 能否区分普通检测状态与近距离危险状态。
- 边线达到设定近距离条件时，能否正确触发停车信号。
- 边线离开触发范围后，检测状态能否正确更新。

## 2.6 demo_edge_blue.py：蓝色矩形框识别与位置输出测试

### 测试目标

单独验证 OpenMV 对蓝色矩形框的识别能力，并实时向下位机输出矩形框的位置。

### 功能要求

1. 检测图像中的蓝色矩形框。
2. 提取当前画面中可识别的矩形边缘、角点或其他有效几何特征。
3. 根据当前可见信息计算矩形框的位置。
4. 将矩形框的位置数据实时发送给下位机，供后续底盘对齐控制使用。
5. 屏幕实时显示距离与标定位置

### 当前存在的视觉限制

由于摄像头视野和车辆进入矩形框时的观察角度受到限制，车辆进入矩形框附近时，OpenMV 可能只能看到矩形框的一个角。

因此，无法保证每一帧图像都能识别到完整矩形框的轮廓和四个角点。

### 待验证的处理思路

可以优先验证一种分阶段对齐策略：

**第一阶段：对齐第一条边**

1. 识别矩形框当前可见的一条边。
2. 根据识别结果计算车辆与该边之间的位置偏差。
3. 控制小车与该边完成对齐。

**第二阶段：对齐相邻边**

1. 在第一条边对齐后，识别与其相邻的另一条边。
2. 根据识别结果计算第二个方向的位置偏差。
3. 控制小车完成第二个方向的对齐。

该方案目前属于待验证思路，并非已经确定的最终算法。

后续需要结合实际摄像头视野、车辆进入方向和矩形框尺寸进行实测，再确定具体实现方式。

### 验收重点

- 能否识别蓝色矩形框的有效边缘或角点。
- 只看到矩形框局部区域时，能否输出当前可用的位置数据。
- 位置数据能否实时更新并发送给下位机。
- 能否为后续分阶段边线对齐控制提供有效信息。

# 三、第二阶段：测试通过后的正式代码结构

当五个测试单元均完成实测，并通过功能验证和代码规范检查后，再将代码整合为正式项目。

## 3.1 正式目录结构

正式项目文件夹命名为：

`src_openmv_repair_vx`

其中，`x` 代表版本号。

例如：

`src_openmv_repair_v1`

正式目录结构固定为：

```text
src_openmv_repair_v1/
├── config.py
├── main.py
└── utils.py
```

## 3.2 文件职责

| 文件 | 主要职责 |
|---|---|
| `config.py` | 集中管理摄像头、识别阈值、通信接口及其他必要配置参数 |
| `utils.py` | 封装可复用的基础功能、小函数及相关工具类 |
| `main.py` | 组织完整视觉任务流程，调用各功能模块完成综合任务 |

具体函数和类的划分，应以实际功能及代码复用关系为依据，避免为了拆分而拆分。

## 3.3 整合原则

- 五个测试单元通过验证后，再进行正式整合。
- 保留已经实测通过的识别算法和参数，不随意改变其行为。
- 将重复使用的底层操作提取为可复用函数或类。
- 由 `main.py` 组织各项视觉任务，形成清晰、可追踪的执行流程。
- 正式版本应保持结构简洁，避免不必要的文件、层级和依赖。

# 四、代码编写规范

所有测试单元及后续正式项目均应遵守以下规范。

## 4.1 命名规范

- 函数名称应准确表达其实际功能。
- 类名称应准确表达其封装的对象或职责。
- 变量名称应具有明确含义，避免使用无法体现用途的名称。
- 命名风格应尽量与原始 `src_openmv` 项目保持一致。

## 4.2 基础函数设计

- 将复杂任务拆分为多个职责单一的小函数。
- 小函数应尽可能具有独立性和复用性。
- 每个小函数只完成一个明确的操作。
- 避免在一个函数中混合图像采集、目标识别、数据处理和通信发送等多个不同职责。

## 4.3 类的封装原则

- 将具有明确关联的多个小函数封装到同一个类中。
- 类应作为一个职责清晰、边界明确的最小功能单元。
- 类内部的小函数负责完成具体操作。
- 类对外提供清晰的调用接口，便于其他功能组合使用。

## 4.4 组合函数设计

组合函数负责完成一个相对完整的任务，应尽可能通过调用基础函数或类来实现，而不是重复编写底层操作。

例如，物料识别任务可以按照以下逻辑组织：

```text
物料识别任务
    ├── 图像采集
    ├── 目标区域提取
    ├── 物料特征识别
    ├── 物料类别判定
    └── 识别结果输出
```

一个组合函数可以负责组织并完成一个完整的 Demo 功能。

## 4.5 模块化与可维护性

- 优先保证功能边界清晰，再考虑代码复用。
- 相同功能不得在多个位置重复实现。
- 修改某一项识别功能时，应尽量避免影响其他功能。
- 测试阶段坚持单文件、单任务原则。
- 正式整合阶段再根据实际需要进行模块化封装。

## 4.6 运行环境与兼容性

- 必须适配 OpenMV H7 Plus 的硬件和运行环境。
- 遵循现有 `src_openmv` 项目使用的 API、语法及库调用方式。
- 不得未经验证直接引入与 OpenMV MicroPython 环境不兼容的 PC 端 OpenCV 或 Python 库。
- 代码应考虑 OpenMV 的运行资源限制，避免不必要的内存占用和重复计算。

# 五、第三阶段：上位机与下位机通信协议（后续任务）

> 本阶段暂不开展。需要先完成五个视觉测试单元，并确认视觉识别结果和输出数据满足要求。

## 5.1 参考文件

- 通信协议参考：`vision.h`、`vision.c`。
- 机械结构参考：项目中已经提供的机械结构相关文件及压缩包。

## 5.2 主要任务

后续需要设计并实现 OpenMV 上位机与 STM32 下位机之间的通信协议。

使下位机能够解析上位机发送的视觉数据，并结合实际机械结构，将视觉结果转换为具体的执行控制量。

## 5.3 需要计算或分配的数据

根据视觉识别结果及机械结构，确定相应执行机构所需的数据，例如：

**1. 夹爪机构**

- 夹爪需要下降的距离；
- 夹爪相关动作参数。

**2. 底盘机构**

- 小车需要执行的运动方向；
- 小车需要执行的运动距离；
- 其他必要的运动控制参数。

**3. 旋转机构**

- 旋转盘需要执行的角度；
- 旋转方向；
- 目标位置及其他必要参数。

**4. 其他机械机构**

根据实际机械结构和任务流程分配必要的控制数据。

## 5.4 设计原则

- 通信数据应具有明确的数据含义和字段定义。
- 上位机输出的数据应能够被下位机稳定解析。
- 视觉识别结果与机械执行参数之间应建立清晰的映射关系。
- 所有动作参数应结合实际机械结构、行程和安装关系确定。
- 不得仅根据视觉算法结果直接猜测机械执行量，必须结合机械结构资料和实测数据进行换算与验证。
